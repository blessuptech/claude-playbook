NaXum · Claude Playbook

Conventions and rules for using Claude on NaXum products. Reference doc, not a tutorial. For tool installation see Anthropic docs. For our specific stack and code rules see CLAUDE.md and audit-rules.md in the relevant repo.

VO migration APF BlessUP / ACT.X Mobile app

I.Ground Rules

1.1 Purpose & Scope

This playbook defines how Claude is used inside NaXum. It does not define what Claude is or how it works generally — that is documented elsewhere. It assumes the reader already has Claude Code installed and access to claude.ai.

Applies to: VO migration (laravel12_vo), the new mobile app, the APF / BuilderPro client project, and BlessUP / ACT.X smart contracts.

1.2 The Harness

Every NaXum repo ships with a Claude harness. Currently in production for the VO. Being rolled out in waves to mobile, APF, and BlessUP.

The harness consists of:

FilePurpose
CLAUDE.mdProject context — stack, conventions, where things live, what tests must pass. Loaded automatically on every Claude Code session.
audit-rules.md95 enforceable rules across 14 categories (PCG-*, VSG-*, TEST-*, PERF-*). Checked by the /audit command.
skills/Custom commands (currently 3: /audit, /commit, /sail-up). New skills get added here.
refs/Reference files — code style guide, conventions, troubleshooting log.

1.3 Standard Commands

CommandWhen to run
/auditBefore every commit. Mandatory on any behavior-changing diff.
/commitAfter /audit passes. Writes the commit message in our format.
/sail-upWhen stuck. Catch-all "help me figure out where to start" command.
/audit-sol(coming) BlessUP smart contract audit. Same idea, Solidity rules.
/audit-light(coming) Faster audit on changed files only, for partial-diff work.

II.The Three Rule Sets

Three categories of non-negotiable rules. Breaking any of them is a stop-everything moment.

2.1 DATA — Security & Confidentiality

DATA-01
No production customer data in Claude. Names, emails, phone numbers, addresses, payment info, member IDs. Not in claude.ai, not in Claude Code, not in screenshots. Anonymize before pasting.
DATA-02
No secrets in any prompt. API keys, JWT secrets, DB credentials, Stripe keys, Apple/Google merchant keys, IPN tokens. Paste the variable name and the error, never the value.
DATA-03
No full .env dumps. Even when debugging env issues. Share schema and error, not values.
DATA-04
The harness is internal. Do not share the contents of audit-rules.md, CLAUDE.md, or custom skills outside NaXum.
DATA-05
Client codebase boundaries. APF / BuilderPro work stays in its repos. BlessUP work stays in its repos. Don't paste BlessUP smart contract code into a session focused on APF, or vice versa.
DATA-06
Staging or seed data only for examples. If you need realistic data shapes, use factory output or anonymized staging dumps.

2.2 CODE — Engineering Rules

CODE-01
Every MR goes through human review. Claude-written code follows the same approval chain as hand-written: frontend → frontend lead, backend → backend lead, infra → infra/architecture leads. Claude does not bypass review.
CODE-02
/audit is required before every commit. Even small changes. Especially Claude-written changes.
CODE-03
The test suite is the source of truth. Current baseline is 888 passing, 0 failing on the VO. If your work drops that, stop and investigate before committing. Don't suppress, skip, or delete failing tests to make the count match.
CODE-04
No silent dependency additions. If Claude suggests installing a new package, the human decides. Justify the add in the MR description.
CODE-05
Stick to the stack. VO is Laravel 12 + Vue 3 + PrimeVue + Tailwind + MySQL 8.4 + JWT. Mobile is Expo + React Native + NativeWind + Zustand + TanStack Query. Don't let Claude introduce Nuxt, Next.js, Redux, styled-components, or alternate ORMs.
CODE-06
Verify before trusting. Confirm file paths, function names, and package versions Claude references actually exist before acting on them. /audit catches most hallucinations but not all.
CODE-07
No protected branch pushes from Claude. Feature branches only. Merge to main / develop is a human action.
CODE-08
Behavior changes need a test. If Claude is changing logic that affects user-visible behavior or money flow (commissions, payouts, billing), it must add or update a test.

2.3 COMM — Client & Team Communication

COMM-01
Claude does not post on your behalf. Drafts only. Basecamp posts, Slack messages, client emails, MR descriptions — all reviewed and sent by a human.
COMM-02
Match the existing voice for the channel. Task specs follow the TASK / NOTES / DONE DONE format. Basecamp posts get a TLDR at top, no em dashes, simple language. Client communication is warmer. Claude defaults toward verbose corporate tone; cut hard.
COMM-03
No fabricated attributions. Don't let Claude write quotes, decisions, or commitments attributed to team members or clients. If Claude generates these in a draft, strip them.
COMM-04
Client-facing content gets a second pass. Anything going to an external stakeholder (APF, BlessUP investors, client champions on the NaXum side) is reviewed before sending.

III.Prompting Conventions

3.1 The CCO Pattern

Every prompt for NaXum work should specify three things. Skip personas, skip "you are a senior engineer," skip chain-of-thought tricks.

ElementWhat to include
ContextRepo, file path, what the codebase calls things, any naming convention Claude wouldn't infer.
ConstraintWhat it must not change. Which patterns to match. Which tests must still pass.
OutcomeWhat "done" looks like. A passing /audit? A green test? A reviewed MR description?

3.2 Prompt Rules

PROMPT-01
Lead with the file path. Almost every coding prompt should name the file Claude is working in. Vague "fix the bug" wastes a turn.
PROMPT-02
Specify what NOT to touch. Claude will refactor adjacent code if not constrained. State the blast radius.
PROMPT-03
Ask for the smallest diff that satisfies the requirement. Default Claude output is over-engineered. "Smallest diff" is a magic phrase.
PROMPT-04
One task per session. Long-running sessions accumulate context bloat and burn the conversation budget. Exit and re-enter between tasks.
PROMPT-05
Don't ask Claude to research external docs from scratch. Point it at the specific docs URL with the question. Don't let it spelunk.

3.3 NaXum-specific examples

Bug triage from a reported issue (VO frontend)

Bad
"Fix the contact download bug that was reported"
Good
"In app/Http/Controllers/ContactsController.php the downloadCsv() method exports every DB column. We want it to export only the columns currently visible in the frontend table — the frontend sends them as visible_columns[] in the request. Don't change the frontend. Add a feature test in tests/Feature/Contacts/DownloadCsvTest.php. Smallest diff that satisfies this."

Adding validation (VO backend)

Bad
"Add username with numbers"
Good
"Username field currently rejects digits via the regex in UserStoreRequest.php. Update the regex to accept digits but reject usernames that are ALL digits — we still want at least one letter. Add the test cases to UserStoreRequestTest.php. Don't change the field length limit or any other rule on this request class."

Understanding a flow (commission engine QA)

Bad
"How does our commission engine work?"
Good
"I'm doing QA on the New VO commission pages. Walk me from CommissionsController down to whichever service or job actually calculates the payout. Files and methods only, no full code. Compare against /reference/phoenix-vo/ if anything differs."

Mobile screen build (Expo + Figma reference)

Bad
"Build the contacts screen from Figma"
Good
"Build app/(tabs)/contacts.tsx matching the Figma node at {nodeId}. Use Expo Router file-based nav, NativeWind for styling, Zustand for the local filter state, TanStack Query for the contacts list fetch. The endpoint is GET /api/contacts. No Redux, no styled-components. Pattern-match the existing (tabs)/training.tsx for screen scaffolding."
The Pattern Bad prompts ask Claude to figure out what you mean. Good prompts tell Claude what you've already figured out, and ask only for the remaining piece.

IV.Role Playbooks

4.1 Frontend Engineer

Vue 3 · Inertia · PrimeVue · Tailwind · Vite
Default workflow — slice port
  1. Open the target slice folder in Claude Code.
  2. Tell Claude which slice and which mockup section.
  3. Let Claude read the equivalent Phoenix component for behavior reference.
  4. Generate the Vue 3 + PrimeVue version, smallest diff.
  5. /audit.
  6. Manually test in browser (Claude can't see pixels).
  7. /commit, push, MR.
Default workflow — MR review
git fetch && git checkout origin/<mr-branch>
claude
> review the diff vs main. flag anything that breaks an audit rule,
> doesn't match our patterns, or looks risky. files + line numbers only.
Avoid
  • Letting Claude introduce new state management beyond what's already in use.
  • Asking Claude to "improve" a working component — it will refactor freely.
  • Skipping manual visual QA. Claude has zero pixel awareness.

4.2 Backend Engineer

Laravel 12 · MySQL 8.4 · JWT · PHPUnit / Pest
Default workflow — feature endpoint
  1. State the route, controller, request class, and expected response shape in the prompt.
  2. Specify which existing endpoint to pattern-match.
  3. Generate controller + form request + test in one diff.
  4. /audit. Run the test suite locally.
  5. /commit.
Default workflow — commission / payout audit
  1. Pick one page or one calculator at a time. Don't ask Claude to audit "the commission engine."
  2. Have Claude diff the new VO logic against /reference/phoenix-vo/.
  3. Get a behavior-diff list before opening the actual VO.
  4. Execute the test plan against office.phoenix-vo.xyz.
  5. Log every issue with: error description, page link, screenshot or video, expected output.
Avoid
  • Letting Claude write database migrations without explicit human review of the SQL.
  • Trusting Claude's understanding of complex commission math without spot-checking against the old Phoenix tool.
  • Asking Claude to add a new caching layer or queue mechanism without team discussion.

4.3 Mobile Engineer

Expo · React Native · NativeWind · Zustand · TanStack Query · EAS Build
Default workflow — new screen
  1. Start from Figma. Provide the screen name and node ID.
  2. Specify the existing screen to pattern-match.
  3. State the endpoint and response shape, and which Zustand slice (if any) it touches.
  4. Generate the screen file plus any new query hook in one diff.
  5. /audit if the mobile harness is in your repo. Otherwise manual review.
Default workflow — EAS build issues

Don't have Claude explore EAS docs. Point it at the last working build config and ask "what's different here that might be missing." Builds fail on env config and App Store Connect API errors. Both are pattern-match problems, not docs problems.

Avoid
  • Letting Claude pick native module versions silently — Expo plugin versions matter.
  • Adding Redux, MobX, or styled-components. Stack is fixed.
  • Generating Detox or Jest tests without verifying they actually run in our CI.

4.4 Product Lead / Coordinator

claude.ai · Basecamp connector · web search
Default workflow — Basecamp thread summary
  1. In claude.ai with the Basecamp connector connected, paste the thread URL.
  2. Ask for: current status, who owes what, decisions made, decisions still open.
  3. Verify any extracted commitments against the actual thread before relying on them.
Default workflow — task spec drafting
  1. Give Claude the format: TASK / NOTES / Page sections with labeled sub-sections / DONE DONE.
  2. State the actual scope, repo, and any prerequisites.
  3. Reject the first draft. Cut by 30%. Ship the second.
Avoid
  • Letting Claude post to Basecamp directly (see COMM-01).
  • Letting Claude estimate hours. Time estimates require human context.
  • Trusting Claude's summary of a long thread without checking the latest comment.

4.5 QA / Reviewer

claude.ai · Claude Code · Detox / Browser DevTools
Default workflow — test plan generation
  1. Open the feature in Claude Code.
  2. Ask for a test plan with edge cases: empty state, max length, special characters, concurrent users, network failure.
  3. Filter the plan to what's actually testable in our environment.
  4. Execute manually. Log issues per the standard format.
Avoid
  • Trusting that a Claude-suggested test case actually catches the intended bug. Run the test against a known-bad version to verify.
  • Letting Claude declare a feature "done" without your manual verification.

V.Anti-patterns

5.1 The Five Common Traps

AP-01
The runaway /audit. One audit run on a 30-file diff can consume 20% of a session. Fix: batch audits by 5-10 files. Reset the session between unrelated tasks. Skip /audit on whitespace-only and comment-only changes.
AP-02
Docs spelunking. Reading official API docs for hours before writing any code. Worst-case observed: 24 hours on StoreKit + Google Billing docs before starting implementation. Fix: when external docs are needed, point Claude at the docs URL with the specific question. 5-10 minutes, not days.
AP-03
Confident hallucination. Claude will invent function names, package versions, and blog post citations with full confidence. Fix: verify file paths and function names exist before acting. Spot-check version numbers. Treat all citations as suspect until proven.
AP-04
The kitchen-sink prompt. Asking Claude to do four things at once. Result is four half-done things. Fix: one task per prompt, one task per session. See PROMPT-04.
AP-05
Skipping /audit on Claude-written code "because Claude wrote it." The audit catches Claude-specific failure modes more often than human-written ones. It is not optional. See CODE-02.

VI.Limits & Escalation

6.1 What Claude won't do (May 2026)

  • See your screen — screenshots must be pasted
  • Access production environments — only your local repo
  • Approve MRs, push to protected branches, or merge
  • Post to Basecamp / Slack / email on your behalf — drafts only
  • Access client production data (and shouldn't try)
  • Replace human review for client-facing decisions
  • Estimate hours reliably
  • Pixel-test UI

6.2 Escalation Path

SituationWhere to go
Harness question (audit rules, CLAUDE.md, custom skills)Harness maintainer thread on Basecamp
Claude Code install / login issueAnthropic docs first, then internal thread
"Should I use Claude for this?"If you have to ask, try it once. If it fails twice, escalate.
Suspected DATA-rule violationStop, do not commit, raise immediately
Claude generated something weird and confidentScreenshot + post in the team thread. Weird cases become future guardrails.
