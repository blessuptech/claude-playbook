The one idea

Most people here use Claude like a search box. The people shipping noticeably faster use it like a teammate they hand real work to. Everything below is about becoming the second kind, on our actual repos.

Tool

Waits for you

  • You type, it autocompletes
  • One line at a time
  • You stay in the driver's seat the whole way
  • Ceiling: maybe 10% faster
Agent

Goes and does it

  • You hand it a whole slice, it drafts the change
  • Reads files, runs tests, reports back
  • You review and decide instead of typing
  • Ceiling: 2–3× on the right work
If one sentence sticks A tool waits for you. An agent goes and does it. Same software, different job. Use it as autocomplete and you get autocomplete results. Hand it whole slices, run a few at once, and review instead of write, and the math changes.
★ If you read nothing else
  1. /audit before every commit — it catches what gets your MR sent back.
  2. One task per session — start fresh between unrelated jobs.
  3. Tell it what not to touch — or it will refactor things you never asked about.
  4. Claude drafts, you review and decide — you own what you ship.
  5. Never paste secrets or real customer data — variable names and errors only.

I · Ground rules

Purpose & scope

This playbook defines how Claude is used inside NaXum, across our products, teams, and workflows. It is not a Claude tutorial; Anthropic's docs cover what Claude is and how to install it. This covers how we use it on our codebases.

It applies across NaXum engineering: the web app (the VO), mobile, BlessUP / ACT.X, and the coordination work around them. It assumes you have Claude Code installed and repo access.

The shape of it Three layers. Rules that are non-negotiable (part II). Conventions for prompting and workflow that earn their keep (parts III–IV). Role defaults so you do not have to assemble your own from scratch (part V).
I · Ground rules

The harness

Every NaXum repo ships with a Claude harness: the setup that makes Claude already know our stack, our rules, and our patterns the moment you open a session. You do not start from a blank prompt. You start from thousands of lines of context that load automatically.

FilePurpose
CLAUDE.mdThe brain. Stack, conventions, where things live, what tests must pass. Loaded automatically every session.
audit-rules.mdThe rule book: 95+ numbered rules across categories (PCG-*, VSG-*, TEST-*, PERF-*). Enforced by /audit.
skills/Custom commands: /audit, /commit, /sail-up. New skills get added here.
refs/Reference docs: stores, composables, DRY structure, identity/auth, branding, plus the PCG and VSG playbooks.
Extend the harness, don't route around it The harness is professional grade. The plan is to keep what is there, fix small gaps (hardcoded paths, a shared command set), and add skills on top (/migrate, /audit-sol). If something in it feels wrong, flag it rather than working around it.

I · Ground rules

Teach the harness back

The harness gets smarter the same way this playbook does: every confident mistake becomes a rule.

The habit Any time you correct Claude, end the session with one more line: "Update CLAUDE.md so you don't make that mistake again." Claude is eerily good at writing rules for itself. Review the diff like any other — CLAUDE.md changes go through MR like everything else.

The compounding. Ten engineers each adding one correction a week is a harness that gets measurably sharper every month. This pairs with DOC-05: the screenshot goes to the thread, the rule goes to the harness.

II · Rule sets

DATA — security & confidentiality

Six rules. Breaking one is a stop-everything moment, not a code-review note.

DATA-01
No production customer data in Claude. Member names, emails, phones, addresses, payment info, member IDs. Not in claude.ai, not in Claude Code, not in screenshots. Anonymize before pasting.
DATA-02
No secrets in any prompt. API keys, JWT secrets, DB credentials, Stripe keys, Apple/Google merchant keys, IPN tokens. Paste the variable name and the error, never the value.
DATA-03
No full .env dumps. Even when debugging env issues. Share the schema and the error, not the values.
DATA-04
The harness is internal. Do not share the contents of audit-rules.md, CLAUDE.md, the PCG/VSG, or custom skills outside NaXum.
DATA-05
Keep codebase boundaries. VO work stays in VO sessions, mobile in mobile, BlessUP in BlessUP. Do not paste contract code into a VO session or vice versa; it pollutes context and leaks scope.
DATA-06
Staging or seed data only for examples. If you need realistic data shapes, use factory output or anonymized staging dumps.
II · Rule sets

CODE — engineering rules

Eight rules. Claude-written code earns no shortcuts through the process.

CODE-01
Every MR goes through human review. Claude-written code follows the same approval chain as hand-written: frontend → frontend lead, backend → backend lead, money pages → backend QA. Claude does not bypass review.
CODE-02
/audit is required before every commit. Even small changes. Especially Claude-written changes. Every MR that comes back is a failure of this step.
CODE-03
The test suite is the source of truth. The VO baseline is 888 passing, 0 failing, 0 skipped. If your work drops that, stop and investigate before committing. Never suppress, skip, or delete a failing test to make the count match.
CODE-04
No silent dependency additions. If Claude suggests installing a new package, the human decides. Justify the add in the MR description.
CODE-05
Stick to the stack. VO is Laravel 12 + Vue 3 + PrimeVue + Tailwind + MySQL 8.4 + JWT. Mobile is Expo + React Native + NativeWind + Zustand + TanStack Query. Do not let Claude introduce Nuxt, Next.js, Redux, styled-components, Bootstrap, or alternate ORMs.
CODE-06
Verify before trusting. Confirm file paths, function names, and package versions Claude references actually exist before acting on them. /audit catches most hallucinations, not all.
CODE-07
No protected-branch pushes from Claude. Feature branches only. Merge to main / develop is a human action.
CODE-08
Behavior changes need a test. If Claude changes logic that affects user-visible behavior or money flow (commissions, payouts, billing), it adds or updates a test.
II · Rule sets

COMM — client & team communication

Four rules. Claude drafts; a person sends.

COMM-01
Claude does not post on your behalf. Drafts only. Basecamp posts, client emails, MR descriptions: all reviewed and sent by a human.
COMM-02
Match the channel's voice. Task specs follow TASK / NOTES / DONE DONE. Basecamp posts get a TLDR at top, no em dashes, simple language. Client comms are warmer. Claude defaults to verbose corporate tone; cut hard.
COMM-03
No fabricated attributions. Do not let Claude invent quotes, decisions, or commitments attributed to teammates or clients. If a draft contains them, strip them.
COMM-04
Client-facing content gets a second pass. Anything going to an external stakeholder is reviewed before sending.
II · Rule sets

DOC — documenting AI-generated work

Using Claude is encouraged. Hiding that you used it is not. These five rules keep AI-generated work reviewable, traceable, and honest, so the next person (and the audit trail) knows what to trust and what to double-check.

DOC-01
You own what you submit. Once your name is on an MR, a Basecamp post, or a doc, it is yours. "Claude wrote it" is never an excuse for a bug, a wrong number, or a bad tone. Read every line before it ships.
DOC-02
Note AI-assisted work in the MR description. One line is enough, e.g. "Slice drafted with Claude Code, reviewed and audited by me." Reviewers calibrate their attention when they know what was machine-drafted.
DOC-03
Flag what you couldn't verify. If Claude produced a number, a citation, or a config value you did not confirm, say so rather than presenting it as checked. Unverified is not the same as wrong, but it must be labeled.
DOC-04
Keep AI-generated docs in our format. Task specs still follow TASK / NOTES / DONE DONE; commit messages still go through /commit. AI output gets edited to our standards, not pasted raw.
DOC-05
Capture the odd ones. When Claude does something surprisingly good or confidently wrong, screenshot it and drop it in the team thread. Today's oddity becomes tomorrow's guardrail or example.
III · Prompting

The CCO pattern

Every prompt for NaXum work specifies three things. Skip personas, skip "you are a senior engineer," skip chain-of-thought tricks. Just Context, Constraint, Outcome.

ElementWhat to include
ContextRepo, file path, what the codebase calls things, any naming convention Claude would not infer.
ConstraintWhat it must not change. Which patterns to match. Which tests must still pass.
OutcomeWhat "done" looks like. A passing /audit? A green test? A reviewed MR description?
The pattern under the pattern Bad prompts ask Claude to figure out what you mean. Good prompts tell Claude what you have already figured out, and ask only for the remaining piece.
III · Prompting

Prompt rules

Six habits that pay for themselves within a session.

PROMPT-01
Lead with the file path. Almost every coding prompt should name the file. A vague "fix the bug" wastes a turn.
PROMPT-02
Specify what NOT to touch. Claude will refactor adjacent code if not constrained. State the blast radius.
PROMPT-03
Ask for the smallest diff that satisfies the requirement. Default output is over-engineered. "Smallest diff" is a magic phrase.
PROMPT-04
Plan first, then build. For anything bigger than a one-liner: "Show me a plan first, then implement." You catch wrong turns before they cost a diff.
PROMPT-05
One task per session. Long sessions accumulate context bloat and burn budget. Exit and re-enter between unrelated tasks.
PROMPT-06
Don't make Claude research external docs from scratch. Point it at the specific docs URL with the question. Do not let it spelunk.
III · Prompting

NaXum examples — bad vs good

Four real shapes of work. Hover a green box and hit Copy to grab the prompt.

Bug triage from a reported issue (VO frontend)

Bad
"Fix the contact download bug that was reported"
Good
"In app/Http/Controllers/ContactsController.php the downloadCsv() method exports every DB column. We want only the columns currently visible in the frontend table — the frontend sends them as visible_columns[] in the request. Don't change the frontend. Add a feature test in tests/Feature/Contacts/DownloadCsvTest.php. Smallest diff."

Adding validation (VO backend)

Bad
"Add username with numbers"
Good
"The username field rejects digits via the regex in UserStoreRequest.php. Update it to accept digits but reject usernames that are ALL digits — at least one letter required. Add the cases to UserStoreRequestTest.php. Don't change the length limit or any other rule on this request class."

Understanding a flow (commission engine QA)

Bad
"How does our commission engine work?"
Good
"I'm doing QA on the new VO commission pages. Walk me from CommissionsController down to whichever service or job actually calculates the payout. Files and methods only, no full code. Compare against the old nxm-office behavior if anything looks different."

Mobile screen build (Expo + Figma reference)

Bad
"Build the contacts screen from Figma"
Good
"Build app/(tabs)/contacts.tsx matching the Figma node {nodeId}. Expo Router file-based nav, NativeWind for styling, Zustand for local filter state, TanStack Query for the contacts fetch. Endpoint is GET /api/contacts. No Redux, no styled-components. Pattern-match the existing (tabs)/training.tsx."
IV · Agentic workflows

Plan mode — pour the energy into the plan

For anything bigger than a one-liner, start in plan mode: hit shift+tab twice. Claude proposes a plan, you iterate on it until it is right, then switch to auto-accept and let it one-shot the implementation.

The workflow plan mode → refine the plan → auto-accept → Claude one-shots it.

The recovery move. The moment a session goes sideways, do not keep pushing and paying for corrections. Switch back to plan mode and re-plan. Two minutes of planning beats twenty minutes of "no, not like that."

Team trick worth stealing Have one Claude write the plan, then open a second session and ask it to review the plan as a staff engineer. Cheap insurance on big slices.
IV · Agentic workflows

Parallel worktrees — three slices at once

The single biggest unlock, popularized by Boris Cherny: run multiple Claude Code sessions at the same time, each in its own git worktree, each on a different slice. One engineer, three slices, same wall-clock.

Worktrees are now built in. One flag, no manual git setup:

claude --worktree slice-4a     # opens an isolated worktree + session
claude --worktree slice-4b     # second terminal, second slice
claude --worktree slice-5a     # third

Prefer clicking? The Claude Desktop app's Code tab has a worktree checkbox that does the same thing.

Why it works The slices are independent, so they do not conflict. Your job stops being "type the code" and becomes "keep three drafts moving and review each one." That is the agent mindset in one command.
Going bigger Subagents can use worktree isolation too. For a large batched change you can ask Claude to "batch the changes and launch parallel agents with worktree isolation, each testing its changes end to end." Use with judgment; the review load is still on you.
▶ Real demo · ACT.X~90 sec
Three agents, one change across three repos
A real session: 3 Claude Code agents at once across actx-contracts, actx-cloud, and blessup-launchpad — exploring backend architecture, reviewing contracts for mergeability, and checking UI/backend integration after the GitHub migration. One engineer directing three streams in parallel.

Append "use subagents" to any request where the work fans out: exploring a codebase, checking a change across many files, researching three options at once. Claude spins up parallel workers and keeps your main session's context clean.

> controllers, services, and jobs. Files and methods only.

IV · Agentic workflows

Claude drafts, you review — invert the work

The slow way: you write the slice from scratch, Claude helps here and there. The fast way: Claude writes the first full draft from the migration plan, and you become the reviewer. Same quality bar, a fraction of the time.

Tool way
Open the files, start typing the port yourself, ask Claude to fill in functions as you go.
Agent way
"Implement slice 4a (manage — simple) by porting from nxm-office to laravel12_vo, following the patterns in CLAUDE.md and the migration plan. Show me a plan first. Then implement, run /audit, and report what changed."

You stay in the loop on judgment and architecture. Claude handles the mechanical lift. You review and correct, not the other way around.

IV · Agentic workflows

/audit before every commit — kill the returns

Returns are the timeline killer. Every MR that bounces back costs a reviewer cycle plus your rework. /audit catches exactly those issues before review. Run it before every single commit. Zero exceptions, zero returns is the standard.

# after Claude finishes a slice, before you commit:
/audit
# fix anything it flags, then:
/commit
War story When the team treats /audit as optional, slices come back. When it is run before every submission, the return rate drops toward zero. One audit run eliminates one return cycle. Multiply that across 34 migration pages.
IV · Agentic workflows

AI-assisted MR review — pre-review before the human

Reviewing is a bottleneck on every team. Before a human opens the diff, have Claude do a first pass: what changed, which audit rules it touches, what looks risky. The human reviewer then signs off in a fraction of the time.

git fetch && git checkout origin/<mr-branch>
claude
> Review this diff vs main. Flag anything that breaks an audit rule,
> doesn't match our patterns, or looks risky. Files + line numbers only.
> Then give me a 5-line summary I can paste into the MR thread.

Reviewer time on a typical MR drops from roughly 30–45 minutes to about 10. The human still makes the call; Claude just clears the underbrush.

IV · Agentic workflows

The migration loop — Gate A / B / C

A big port (like nxm-office → laravel12_vo) runs slice by slice through a three-gate method. Each gate is a human checkpoint; Claude does the work inside each phase, you approve between them.

GateClaude doesYou do
A · TraceReads the source page, writes a trace doc: what it does, what it touches.Approve the understanding before any code.
B · BuildImplements the slice, runs /audit, verifies tests.Review the diff and audit result.
C · MRDrafts the MR description in our format.Final review, then submit.

The /migrate skill (coming) automates Gate A's trace-doc step so each slice starts faster than the last.

IV · Agentic workflows

One hook, fewer audit flags

A PostToolUse hook auto-formats every file Claude writes, so formatting never reaches /audit in the first place:

"PostToolUse": [
  { "matcher": "Write|Edit", "hooks": [
    { "type": "command", "command": "npm run format || true" }
  ]}
]

Check it into the repo's .claude/settings.json once; the whole team benefits. Swap the command per repo (Pint for Laravel, Prettier for the frontend and mobile).

Vue 3 · PrimeVue · Tailwind · Pinia

VI · Anti-patterns

The five common traps

The failure modes that show up again and again. Name them and you stop repeating them.

AP-01
The runaway /audit. One audit on a 30-file diff can eat 20% of a session. Fix: batch audits by 5–10 files. Reset the session between unrelated tasks. Skip /audit on whitespace- and comment-only changes.
AP-02
Docs spelunking. Reading official API docs for hours before writing any code. Worst case observed: 24 hours on StoreKit + Google Billing docs before starting. Fix: point Claude at the docs URL with the specific question. 5–10 minutes, not days.
AP-03
Confident hallucination. Claude will invent function names, package versions, and citations with full confidence. Fix: verify paths and function names exist before acting. Spot-check versions. Treat citations as suspect until proven.
AP-04
The kitchen-sink prompt. Asking Claude to do four things at once. Result: four half-done things. Fix: one task per prompt, one task per session. See PROMPT-05.
AP-05
Skipping /audit "because Claude wrote it." The audit catches Claude-specific failure modes more often than human ones. It is not optional. See CODE-02.
VII · Troubleshooting

Claude did X — do Y

The come-back-again section. Find the symptom, apply the fix.

Symptom: scope creep, "helpful" refactors of adjacent code
Editing files you told it not to touch. Restate the blast radius: "Only change X. Do not modify any other file." Add "smallest diff." If it already sprawled, git checkout the files it should not have touched and re-run with tighter constraints. See PROMPT-02.
Symptom: confident reference to something not in the repo
Invented a function / file / package. Do not act on it. Ask Claude to grep and confirm first: "Find the definition of X before using it." Spot-check versions against composer.json / package.json. See AP-03.
Symptom: context bloat from a long, multi-task session
Slow, forgetful, repeating itself. Exit and start a fresh session. Context accumulates and degrades over a long chat. One task per session keeps it sharp. See PROMPT-05.
Symptom: same MR bounces back with new issues each time
MR keeps getting returned. You are almost certainly not running /audit before committing. Run it every time and fix everything it flags. Also check: pipeline green? Draft removed? Real screenshots? Checklist complete? Rebased on main? See CODE-02.
Symptom: suggests Redux, Next.js, a new ORM, an extra dependency
Wants to change the stack. Say no by default. The stack is fixed (CODE-05). A genuine add is a human decision; justify it in the MR. Do not let Claude add it silently (CODE-04).
Symptom: long research loops on StoreKit / billing / EAS
Reading docs forever, no code. Stop it. Point it at the exact docs URL with the exact question, or at the last working config: "What's different here that's missing?" Most are pattern-match problems. See AP-02.
Symptom: green test, false confidence
Test passes but doesn't catch the bug. Run it against a known-bad version of the code. If it still passes, the test is worthless; tell Claude exactly what behavior it must fail on. See the QA playbook.
Symptom: verbose corporate tone, em dashes, invented quotes
Draft sounds robotic. Cut hard. Basecamp: TLDR at top, simple language, no em dashes. Strip any quote or commitment attributed to a person (COMM-03). Claude drafts, a human sends (COMM-01).
Found a new failure mode? Screenshot it and post it in the team thread. Confident mistakes become the next entry here; that is how this section gets useful.
VIII · Limits

What Claude won't do

Know the edges so you do not waste a session pushing against them.

  • See your screen — screenshots must be pasted
  • Access production environments — only your local repo
  • Approve MRs, push to protected branches, or merge
  • Post to Basecamp / Slack / email on your behalf — drafts only
  • Access client or member production data (and should not try)
  • Replace human review for client-facing decisions
  • Estimate hours reliably
  • Pixel-test UI

IX · Models & budget

Which model, when

Claude Code lets you pick the model with /model. Picking right is the single biggest lever on both quality and credits — bigger is not always better, and smaller is not always cheaper.

WorkModelWhy
Migration slices, debugging, architecture, money pages, contract codeThe strongest your plan offers (Fable 5 / Opus-class)Less steering. It gets the intent in one turn instead of three. A bigger model that one-shots the task is usually cheaper in total than a smaller one you babysit.
Bulk mechanical work: renames, translations, formatting, boilerplate tests, commit messagesSonnet-classPlenty smart for pattern work at a fraction of the burn.
Quick lookups, "what does this regex do", summaries of short filesHaiku-classDo not spend Opus money on questions a fast model answers identically.
The logic, from the creator of Claude Code "It's the best coding model I've ever used, and even though it's bigger and slower, since you have to steer it less and it's better at tool use, it is almost always faster than using a smaller model in the end." Steering cost is real cost.

Lineup moves. This card follows. As of June 2026 the family is Fable 5 (newest, most capable), Opus 4.8, Sonnet 4.6, Haiku 4.5. When Anthropic ships a new model, this card gets updated and tagged NEW. Day to day, trust /model over memory.

IX · Models & budget

Effort — the dial nobody uses

/model also sets an effort level: low, medium, high. It is a second, quieter lever on burn.

EffortUse for
HighReal engineering: slices, debugging, anything touching money flow.
MediumRoutine edits in a codebase Claude already knows from the harness.
LowMechanical bulk where the pattern is obvious and volume is high.
Calibrate to our budget, not Boris's The Claude Code team runs high effort on everything — they also do not share a team plan. Default high for real work, drop deliberately for bulk, and never debug commissions on low.
IX · Models & budget

/compact vs /clear

The two context commands everyone confuses. Wrong choice burns credits or loses your thread.

CommandWhat it doesUse when
/clearWipes the session. Blank slate.Between unrelated tasks. Pairs with PROMPT-05.
/compactSqueezes the history into a summary, keeps the thread, frees context.Mid-task when the session is getting long but you still need what happened.

Compact at a natural pause, not mid-edit. Auto-compact exists as a safety net; do not lean on it during critical work — pick the moment yourself, right after a commit is a good one.

See the meter Run /statusline once and have it show remaining context and cost. You cannot manage what you cannot see; half the team discovers they were at 90% context only when Claude starts forgetting.
IX · Models & budget

COST rules

Six rules. Every one of these is a real credit leak we have already paid for.

COST-01
One task per session. Context bloat is the silent burner. Long mixed sessions cost more per answer and the answers get worse. (Same rule as PROMPT-05, promoted to a money rule.)
COST-02
Match the model to the job. Bulk renames on the biggest model wastes credits; money-math debugging on the smallest wastes a day. See the table on the first card of this part.
COST-03
Plan first on anything non-trivial. A wrong implementation paid for twice costs more than a plan paid for once. Plan mode exists for this (part IV).
COST-04
Batch the audits. 5 to 10 files per /audit run. One audit on a 30-file diff can eat 20% of a session. (See AP-01.)
COST-05
Point, don't spelunk. Docs URL plus the specific question. Never "go research X." (See AP-02 — the 24-hour StoreKit story.)
COST-06
Reuse, don't re-derive. Anything you prompt more than once a day becomes a skill or slash command, checked into the repo. Repeated prompting is repeated spend.
