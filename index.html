NaXum · Claude Playbook

How we use Claude across NaXum — the conventions, workflows, and guardrails that turn Claude from a tool you poke into an agent that does the work. The field guide, not the manual. Pair it with the harness in your repo.

0.Start Here

The one idea

If you take one thing from this whole page, take this:

The shift A tool waits for you to use it. An agent works while you sleep. Most of the team is using Claude Code as a fancy autocomplete. The people moving 2–3× faster are using it as an agent — handing it whole slices, running three at once, and reviewing the output instead of typing it.
Tool mindset

You drive every keystroke

  • "Write this one function for me."
  • One chat, one task, you watching the whole time.
  • You write the slice; Claude tidies it.
  • Review is manual and slow. Returns pile up.
  • Speed gain: ~10–20%.
Agent mindset

You direct, verify, and decide

  • "Implement slice 4a from the migration plan. Plan first, then build."
  • Three worktrees, three slices, in parallel.
  • Claude drafts the slice; you review and correct.
  • /audit runs before every commit, so MRs land clean.
  • Speed gain: 2–3×.
War story · why this matters On a recent migration push, several slices came back from review with new issues. Each return burns a full cycle — reviewer time, rework, rebase, re-review. That's not a coding problem. It's a pre-submission quality problem that /audit eliminates entirely. The whole point of this playbook is to make returns rare.

How to read this

  • Already coding with it? Jump to IV · Agentic Workflows — that's where the speed lives.

I.Ground Rules

1.1 Purpose & Scope

This playbook defines how Claude is used inside NaXum — across our products, teams, and workflows. It is not a Claude tutorial; Anthropic's docs cover what Claude is and how to install it. This covers how we use it on our codebases.

Applies across NaXum engineering — web (the VO), mobile, and the work around them. It assumes you have Claude Code installed and repo access.

1.2 The Harness

Every NaXum repo ships with a Claude harness — the setup that makes Claude already know our stack, our rules, and our patterns the moment you open a session. You don't start from a blank prompt; you start from thousands of lines of context that load automatically.

FilePurpose
CLAUDE.mdThe brain. Stack, conventions, where things live, what tests must pass. Loaded automatically every session.
audit-rules.mdThe rule book — 95+ numbered rules across categories (PCG-*, VSG-*, TEST-*, PERF-*). Enforced by /audit.
skills/Custom commands: /audit, /commit, /sail-up. New skills get added here.
refs/Reference docs — Pinia stores, composables, DRY structure, identity/auth, branding, plus the PCG and VSG playbooks.
Don't rewrite the harness — extend it The harness is professional grade. The plan is to keep what's there, fix small gaps (hardcoded paths, a shared command set), and add skills on top (/migrate, /audit-sol). If something in the harness feels wrong, flag it — don't route around it.

II.The Three Rule Sets

Three categories of non-negotiable rules. Breaking a DATA rule is a stop-everything moment.

2.1 DATA — Security & Confidentiality

DATA-01
No production customer data in Claude. Member names, emails, phones, addresses, payment info, member IDs. Not in claude.ai, not in Claude Code, not in screenshots. Anonymize before pasting.
DATA-02
No secrets in any prompt. API keys, JWT secrets, DB credentials, Stripe keys, Apple/Google merchant keys, IPN tokens. Paste the variable name and the error, never the value.
DATA-03
No full .env dumps. Even when debugging env issues. Share the schema and the error, not the values.
DATA-04
The harness is internal. Don't share the contents of audit-rules.md, CLAUDE.md, the PCG/VSG, or custom skills outside NaXum.
DATA-05
Keep codebase boundaries. VO work stays in VO sessions, mobile in mobile, BlessUP in BlessUP. Don't paste contract code into a VO session or vice versa — it pollutes context and leaks scope.
DATA-06
Staging or seed data only for examples. If you need realistic data shapes, use factory output or anonymized staging dumps.

2.2 CODE — Engineering Rules

CODE-01
Every MR goes through human review. Claude-written code follows the same approval chain as hand-written: frontend → frontend lead, backend → backend lead, money pages → backend QA. Claude does not bypass review.
CODE-02
/audit is required before every commit. Even small changes. Especially Claude-written changes. Every return that comes back is a failure of this step.
CODE-03
The test suite is the source of truth. The VO baseline is 888 passing, 0 failing, 0 skipped. If your work drops that, stop and investigate before committing. Never suppress, skip, or delete a failing test to make the count match.
CODE-04
No silent dependency additions. If Claude suggests installing a new package, the human decides. Justify the add in the MR description.
CODE-05
Stick to the stack. VO is Laravel 12 + Vue 3 + PrimeVue + Tailwind + MySQL 8.4 + JWT. Mobile is Expo + React Native + NativeWind + Zustand + TanStack Query. Don't let Claude introduce Nuxt, Next.js, Redux, styled-components, Bootstrap, or alternate ORMs.
CODE-06
Verify before trusting. Confirm file paths, function names, and package versions Claude references actually exist before acting on them. /audit catches most hallucinations, not all.
CODE-07
No protected-branch pushes from Claude. Feature branches only. Merge to main / develop is a human action.
CODE-08
Behavior changes need a test. If Claude changes logic that affects user-visible behavior or money flow (commissions, payouts, billing), it adds or updates a test.

2.3 COMM — Client & Team Communication

COMM-01
Claude does not post on your behalf. Drafts only. Basecamp posts, client emails, MR descriptions — all reviewed and sent by a human.
COMM-02
Match the channel's voice. Task specs follow TASK / NOTES / DONE DONE. Basecamp posts get a TLDR at top, no em dashes, simple language. Client comms are warmer. Claude defaults to verbose corporate tone — cut hard.
COMM-03
No fabricated attributions. Don't let Claude invent quotes, decisions, or commitments attributed to teammates or clients. If a draft contains them, strip them.
COMM-04
Client-facing content gets a second pass. Anything going to an external stakeholder is reviewed before sending.

III.Prompting Conventions

3.1 The CCO Pattern

Every prompt for NaXum work specifies three things. Skip personas, skip "you are a senior engineer," skip chain-of-thought tricks. Just Context, Constraint, Outcome.

ElementWhat to include
ContextRepo, file path, what the codebase calls things, any naming convention Claude wouldn't infer.
ConstraintWhat it must not change. Which patterns to match. Which tests must still pass.
OutcomeWhat "done" looks like. A passing /audit? A green test? A reviewed MR description?

3.2 Prompt Rules

PROMPT-01
Lead with the file path. Almost every coding prompt should name the file. Vague "fix the bug" wastes a turn.
PROMPT-02
Specify what NOT to touch. Claude will refactor adjacent code if not constrained. State the blast radius.
PROMPT-03
Ask for the smallest diff that satisfies the requirement. Default Claude output is over-engineered. "Smallest diff" is a magic phrase.
PROMPT-04
Plan first, then build. For anything bigger than a one-liner: "Show me a plan first, then implement." You catch wrong turns before they cost a diff.
PROMPT-05
One task per session. Long sessions accumulate context bloat and burn budget. Exit and re-enter between unrelated tasks.
PROMPT-06
Don't make Claude research external docs from scratch. Point it at the specific docs URL with the question. Don't let it spelunk.

3.3 NaXum-specific examples

Bug triage from a reported issue (VO frontend)

Bad
"Fix the contact download bug that was reported"
Good
"In app/Http/Controllers/ContactsController.php the downloadCsv() method exports every DB column. We want only the columns currently visible in the frontend table — the frontend sends them as visible_columns[] in the request. Don't change the frontend. Add a feature test in tests/Feature/Contacts/DownloadCsvTest.php. Smallest diff."

Adding validation (VO backend)

Bad
"Add username with numbers"
Good
"The username field rejects digits via the regex in UserStoreRequest.php. Update it to accept digits but reject usernames that are ALL digits — at least one letter required. Add the cases to UserStoreRequestTest.php. Don't change the length limit or any other rule on this request class."

Understanding a flow (commission engine QA)

Bad
"How does our commission engine work?"
Good
"I'm doing QA on the new VO commission pages. Walk me from CommissionsController down to whichever service or job actually calculates the payout. Files and methods only, no full code. Compare against the old nxm-office behavior if anything looks different."

Mobile screen build (Expo + Figma reference)

Bad
"Build the contacts screen from Figma"
Good
"Build app/(tabs)/contacts.tsx matching the Figma node {nodeId}. Expo Router file-based nav, NativeWind for styling, Zustand for local filter state, TanStack Query for the contacts fetch. Endpoint is GET /api/contacts. No Redux, no styled-components. Pattern-match the existing (tabs)/training.tsx."
The pattern Bad prompts ask Claude to figure out what you mean. Good prompts tell Claude what you've already figured out, and ask only for the remaining piece.

IV.Agentic Workflows

This is where the 2–3× lives. Five workflows that turn Claude from a tool into an agent. If Parts I–III are the rules of the road, this is how you actually drive.

4.1 Parallel worktrees — three slices at once

The single biggest productivity unlock (popularized by Boris Cherny): run multiple Claude Code sessions at the same time, each in its own git worktree, each on a different slice. One engineer, three slices, same wall-clock.

Instead of working slices 4a → 4b → 5a one after another, spin up three worktrees and let Claude draft all three in parallel while you review:

git worktree add ../vo-slice-4a feat/slice-4a
git worktree add ../vo-slice-4b feat/slice-4b
git worktree add ../vo-slice-5a feat/slice-5a

# Open 3 terminals. Run `claude` in each.
# Give each one its slice from the migration plan:
#   "Implement slice 4a — manage simple — following the exact
#    patterns in CLAUDE.md. Show me a plan first, then implement."
# Claude Code drafts. You review and correct.
Why it works The slices are independent, so they don't conflict. Your job stops being "type the code" and becomes "keep three drafts moving and review each one." That's the agent mindset in one command.

4.2 Claude drafts, you review — invert the work

The slow way: you write the slice from scratch, Claude helps here and there. The fast way: Claude writes the first full draft from the migration plan, and you become the reviewer. Same quality bar, a fraction of the time.

Tool way
Open the files, start typing the port yourself, ask Claude to fill in functions as you go.
Agent way
"Implement slice 4a (manage — simple) by porting from nxm-office to laravel12_vo, following the patterns in CLAUDE.md and the migration plan. Show me a plan first. Then implement, run /audit, and report what changed."

You stay in the loop on judgment and architecture. Claude handles the mechanical lift. You review and correct — not the other way around.

4.3 /audit before every commit — kill the returns

Returns are the timeline killer. Every MR that bounces back costs a reviewer cycle plus your rework. /audit is the tool that catches exactly those issues before review. Run it before every single commit. Zero exceptions, zero returns is the standard. 

# after Claude finishes a slice, before you commit:
/audit
# fix anything it flags, then:
/commit
War story When the team treats /audit as optional, slices come back. When it's run before every submission, the return rate drops toward zero. One audit run eliminates one return cycle. Multiply that across 34 migration pages.

4.4 AI-assisted MR review — pre-review before the human

Reviewing is a bottleneck on every team. Before a human opens the diff, have Claude do a first pass: what changed, which audit rules it touches, what looks risky. The human reviewer then signs off in a fraction of the time. 

git fetch && git checkout origin/<mr-branch>
claude
> Review this diff vs main. Flag anything that breaks an audit rule,
> doesn't match our patterns, or looks risky. Files + line numbers only.
> Then give me a 5-line summary I can paste into the MR thread.

Reviewer time on a typical MR drops from ~30–45 min to ~10. The human still makes the call — Claude just clears the underbrush.

4.5 The migration loop — Gate A / B / C

A big port (like nxm-office → laravel12_vo) runs slice by slice through a three-gate method. Each gate is a human checkpoint — Claude does the work inside each phase, you approve between them.

GateClaude doesYou do
A · TraceReads the source page, writes a trace doc: what it does, what it touches.Approve the understanding before any code.
B · BuildImplements the slice, runs /audit, verifies tests.Review the diff + audit result.
C · MRDrafts the MR description in our format.Final review, then submit.

The /migrate skill (coming) automates Gate A's trace-doc step so each slice starts faster than the last.

V.Role Playbooks

Find your name. Each role gets a default agentic workflow and an explicit Avoid list.

5.1 Frontend Engineer

Vue 3 · PrimeVue · Tailwind · Pinia · Vite
Default workflow — slice port (agentic)
  1. Set up worktrees for the slices you own (4.1). Don't work them sequentially.
  2. In each session: "Implement slice X following CLAUDE.md and the migration plan. Plan first, then build."
  3. Let Claude draft. You review against the PCG and VSG.
  4. /audit — fix everything it flags.
  5. Manual visual QA in the browser (Claude can't see pixels). Use /sail-up to compare old vs new.
  6. /commit, push, MR.
Avoid
  • Writing slices from scratch when Claude can draft them. You're the reviewer now.
  • Submitting an MR without running /audit. That's where returns come from.
  • Letting Claude introduce new state management or skip the VSG button taxonomy.
  • Skipping manual visual QA. Claude has zero pixel awareness.

5.2 Backend Engineer

Laravel 12 · MySQL 8.4 · JWT · PHPUnit / Pest
Default workflow — feature endpoint
  1. State the route, controller, request class, and expected response shape in the prompt.
  2. Name the existing endpoint to pattern-match.
  3. Have Claude generate controller + form request + test in one diff, plan first.
  4. /audit. Run the test suite locally — baseline is 888 green.
  5. /commit.
Default workflow — money-page QA
  1. Pick one calculator or page at a time. Never "audit the commission engine" in one go.
  2. Have Claude diff the new VO logic against the old nxm-office behavior.
  3. Get a behavior-diff list before opening the actual page.
  4. Log every issue: description, page link, screenshot/video, expected output.
Avoid
  • Letting Claude write DB migrations without human review of the SQL.
  • Trusting Claude's commission math without spot-checking against the old tool.
  • Adding a caching layer or queue mechanism without team discussion.

5.3 Mobile Engineer

Expo · React Native · NativeWind · Zustand · TanStack Query · EAS Build
Default workflow — new screen
  1. Start from Figma. Provide the screen name and node ID.
  2. Name the existing screen to pattern-match.
  3. State the endpoint, response shape, and which Zustand slice it touches.
  4. Claude drafts the screen file + any new query hook in one diff. Plan first.
  5. Review, then /audit (or manual review if the mobile harness isn't in your repo yet).
Default workflow — EAS build issues

Don't have Claude explore EAS docs for hours. Point it at the last working build config: "What's different here that might be missing?" Builds fail on env config and App Store Connect API errors — both are pattern-match problems, not docs problems.

Avoid
  • Submitting an MR that's still DRAFT, with a failing pipeline, empty screenshots, or an unchecked checklist. Fix those before requesting review.
  • Letting Claude pick native module versions silently — Expo plugin versions matter.
  • Adding Redux, MobX, or styled-components. Stack is fixed.

5.4 Product Lead / Coordinator

claude.ai · Basecamp CLI + Skill · web search
Default workflow — Basecamp thread summary
  1. With the Basecamp Skill connected to Claude Code (or the connector in claude.ai), point it at the thread.
  2. Ask for: current status, who owes what, decisions made, decisions still open.
  3. Verify any extracted commitment against the actual thread before relying on it.

Default workflow — task spec drafting
  1. Give Claude the format: TASK / NOTES / DONE DONE.
  2. State the real scope, repo, and prerequisites.
  3. Reject the first draft. Cut by 30%. Ship the second.
Avoid

5.5 QA / Reviewer

claude.ai · Claude Code · Browser DevTools
Default workflow — AI-assisted review
  1. Run the pre-review prompt (4.4) on the diff before manual review.
  2. Read Claude's flagged risks first, then verify the high-risk ones yourself.
  3. For test plans: ask for edge cases — empty state, max length, special chars, concurrent users, network failure.
  4. Filter to what's testable in our environment. Execute manually. Log per standard format.
Avoid
  • Trusting that a Claude-suggested test actually catches the bug. Run it against a known-bad version to verify.
  • Letting Claude declare a feature "done" without your manual verification.

VI.Anti-patterns

6.1 The Five Common Traps

AP-01
The runaway /audit. One audit on a 30-file diff can eat 20% of a session. Fix: batch audits by 5–10 files. Reset the session between unrelated tasks. Skip /audit on whitespace- and comment-only changes.
AP-02
Docs spelunking. Reading official API docs for hours before writing any code. Worst case observed: 24 hours on StoreKit + Google Billing docs before starting. Fix: point Claude at the docs URL with the specific question. 5–10 minutes, not days.
AP-03
Confident hallucination. Claude will invent function names, package versions, and citations with full confidence. Fix: verify paths and function names exist before acting. Spot-check versions. Treat citations as suspect until proven.
AP-04
The kitchen-sink prompt. Asking Claude to do four things at once. Result: four half-done things. Fix: one task per prompt, one task per session. See PROMPT-05.
AP-05
Skipping /audit "because Claude wrote it." The audit catches Claude-specific failure modes more often than human ones. It is not optional. See CODE-02.

VII.Troubleshooting

7.1 "Claude did X — do Y"

The come-back-again section. When Claude misbehaves, find the symptom and apply the fix. Click to expand.

Claude is editing files I told it not to touch
Symptom: scope creep, "helpful" refactors of adjacent code.
Restate the blast radius explicitly: "Only change X. Do not modify any other file." Add "smallest diff." If it already sprawled, git checkout the files it shouldn't have touched and re-run with tighter constraints. See PROMPT-02.
Claude invented a function / file / package that doesn't exist
Symptom: confident reference to something that isn't in the repo.
Don't act on it. Ask Claude to grep and confirm the symbol exists first: "Find the definition of X before using it." Spot-check package versions against composer.json / package.json. /audit catches many of these. See AP-03.
The session feels slow / forgetful / is repeating itself
Symptom: context bloat from a long, multi-task session.
Exit and start a fresh session. Context accumulates and degrades over a long chat. One task per session keeps it sharp. See PROMPT-05.
My MR keeps getting returned in review
Symptom: same MR bounces back with new issues each time.
You're almost certainly not running /audit before committing. Run it before every commit and fix everything it flags. Also check: pipeline green? Draft status removed? Real screenshots (not the template "...")? Checklist fully checked? Rebased on latest main? See CODE-02, 4.3.
Claude wants to install a new package or change the stack
Symptom: suggests Redux, Next.js, a new ORM, Bootstrap, an extra dependency.
Say no by default. Our stack is fixed (CODE-05). If you genuinely think the add is warranted, that's a human decision — justify it in the MR. Don't let Claude add it silently. See CODE-04.
Claude has spent forever reading docs and hasn't written code
Symptom: long research loops, especially on StoreKit / billing / EAS.
Stop it. Point it at the exact docs URL with the exact question, or at the last working config: "What's different here that's missing?" Most of these are pattern-match problems, not docs problems. See AP-02.
Claude wrote a test that passes but doesn't actually catch the bug
Symptom: green test, false confidence.
Run the test against a known-bad version of the code. If it still passes, the test is worthless — tell Claude exactly what behavior it must fail on. See QA playbook (5.5).
Claude drafted a Basecamp post / client email and it sounds robotic
Symptom: verbose corporate tone, em dashes, invented quotes.
Cut hard. Basecamp: TLDR at top, simple language, no em dashes. Strip any quote or commitment attributed to a person (COMM-03). And remember — Claude drafts, a human sends (COMM-01).
Found a new failure mode? Screenshot it and post it in the team thread. Weird, confident mistakes become the next entry here — that's how this section gets useful.

VIII.Limits & Escalation

8.1 What Claude won't do

  • See your screen — screenshots must be pasted
  • Access production environments — only your local repo
  • Approve MRs, push to protected branches, or merge
  • Post to Basecamp / Slack / email on your behalf — drafts only
  • Access client or member production data (and shouldn't try)
  • Replace human review for client-facing decisions
  • Estimate hours reliably
  • Pixel-test UI

8.2 Escalation Path

Harness question (audit rules, CLAUDE.md, custom skills)AI lead / harness maintainer thread on Basecamp
Claude Code install / login / access issueAnthropic docs first, then the internal thread (your coordinator for access)
